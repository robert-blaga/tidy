# When nothing fits

The fallback. Read this when no approved skill in `index.md` covers the user's input.

If a skill DOES cover the input, do NOT use this fallback — read the skill and follow it.

## The loop

1. **Look at the input.** Use whatever tools fit to understand what it is.
2. **Look at the user's setup.** Read-only. How do they organize, what have they taught you, what shape does this fit?
3. **Commit to a hypothesis.** Even with thin, weird, or ambiguous input — pick your best guess at what the user wants done with it. One concrete action. The user will redirect you if you're wrong.
4. **Reply to the user with the full proposal.** Your hypothesis, the evidence you found, the concrete action you'd take, and the skill markdown you'd write to handle this shape next time. All of it goes in the user-facing message — not just the log.
5. **On approval, act and write the skill.** Log the batch per `how-to-log.md` regardless of outcome. Skill naming and format in `how-to-update-the-wiki.md`.

## Don't deflect

The input being ambiguous is not a reason to bounce it back. The user handed it to you to test your judgment. Investigate, then propose.

- ❌ "What do you want me to do with this?"
- ❌ "Did you mean X, Y, or Z?"
- ✅ "I think this is X. I'd do Y. Next time I'd handle it via skill Z. Sound right?"

No menus. Pick one. The user picks differently if you're off.

## Be honest about missing tools

If the right action needs a tool that isn't installed, say so plainly and offer the install as part of the proposal. Don't pretend you can do the work without it.
